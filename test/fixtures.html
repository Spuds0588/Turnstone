Turnstone — fixture sweep

Every supported format, loaded through the real app in the iframe at the bottom of this page, and checked against one shared target: 10 tasks · 4 columns in CSV order · 3 complete · 7 visible. The assertions are made against what the app renders — its own card and counter elements — not against its internal state, so this is the same evidence a user would give.

Below the format sweep are three more sections: the real-world workflow queues, portal lists (where no row holds a link at all), and the two ways a list arrives with no file — email and paste.

Which edition is under test is a query parameter, so the same sweep runs against every artifact: the default is the web app (?app=../app.html&fixtures=../); against the standalone build, test/fixtures.html, turnstone-standalone.html and the sample-links.* files are copied into one directory and opened with ?app=turnstone-standalone.html&fixtures=./ — which is how the offline build is proven to read every format with nothing else beside it. Add &expectLayers=0 for an edition that deliberately ships without MailLayer/PhoneLayer.

HTML, XML and DOCX only reach their matrix through DOMParser, so they are testable here and nowhere else. node test/run.js covers the rest: the parsers, the detection layer, the DOCX container, and generated xls/xlsm/xlsb/ods workbooks.

Refusals — the formats Turnstone declines on purpose

    Real-world workflows — the lists this work actually arrives as

    The fixtures above are one list in eleven encodings: they answer "does format X parse?". These answer the different question — "does Turnstone work on a real queue?" — with the shapes that recur in admin and back-office work: a service-desk queue, an approvals workbook, a vendor tracker, a renewals register, a meeting action log. Each is awkward the way the real thing is: the identifier column comes first and the title sits in the middle, statuses are spelled the way the system spells them, and four of them hold no link anywhere at all. Generated by assets/make-fixtures.js, which emits every fixture in this repo from one definition.

      Portal lists — work that lives behind one URL

      Four of the lists above have no link in them because each row is a key into a system, and the work happens there. This section drives the prompt that offers to rebuild a link from the row, then applies a template through the app's own interface and checks the hrefs that come out — including that the choice survives a reload, and that declining it is remembered too.

        Email and paste — the two ways a list arrives with no file at all

        A forwarded queue, a digest mail, a page saved from a system that will not export, and the simplest path there is: copy a table out of a portal and paste it. All four go through the real handlers.

          Workspace links — a list that arrives inside the URL

          Four ways to get a queue the app cannot fetch: a compressed payload in the fragment, a plain one, one with a portal template beside it, and one that arrives by editing the address bar of a page that is already open. The payloads below are built by this harness, not by the app, so the encoder and the decoder are independent implementations.

              The app under test

              This iframe is ../app.html itself, with a cache-busting parameter. Every service worker on this origin is unregistered and all caches are dropped before it loads, so a stale precache can never make a correct app look broken (or a broken one look correct). Serve the repo root over HTTP: python3 -m http.server 8151, then open test/fixtures.html.
